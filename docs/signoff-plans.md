# 프로젝트 사인오프 계획

상용 플로우의 검증 범위는 칩 용도와 단계에 따라 다르다. 모든 설계에 DFT, 저전력 또는 열 해석을
같게 강제하거나, 반대로 공통 기본값을 코드 밖에서 암묵적으로 빼면 게이트의 의미를 감사할 수 없다.
프로젝트 사인오프 계획은 각 단계의 **필수 도메인 목록을 명시적인 버전**으로 관리한다.

프로젝트 화면의 **Shift-left 스테이지 게이트 → 프로젝트 사인오프 계획**에서 현재 단계의 필수
도메인을 확인한다. approver 이상만 목록과 변경 사유를 저장할 수 있다. 저장은 기존 행을 덮어쓰지
않고 새 버전을 추가한다. 낙관적 버전 검사 때문에 두 사용자가 같은 버전을 동시에 수정하면 한쪽은
409를 받고 최신 계획을 다시 확인해야 한다. AI는 계획을 생성하거나 변경하지 않는다.

기본 계획은 코드에 정의된 기존 단계 매트릭스이며 버전 0으로 표시한다. 사용자 정의 계획이 없으면
기존 동작과 같다. 저전력 설계는 필요한 단계에 `low_power`를 추가할 수 있고, DFT 미적용 설계는
변경 사유와 승인자 신원을 남겨 해당 단계에서 제외할 수 있다. 필수 도메인은 최소 하나여야 하며
중복은 거부한다.

API:

- `GET /projects/{id}/signoff-plan`: 단계별 현재 계획
- `PUT /projects/{id}/signoff-plan/{stage}`: `expected_version`, `required_domains`, `reason`으로 새 버전 저장
- `GET /projects/{id}/signoff-plan/history`: append-only 변경 이력; `stage`, `before_id`, `limit` 지원

게이트 응답의 `plan`에는 source, version, required_domains, 변경 사유와 신원이 포함된다. 게이트 JSON,
검증된 근거 ZIP, 사람의 사인오프 결정에도 같은 계획 스냅샷이 들어가므로 이후 계획 변경이 과거
승인 근거를 바꾸지 않는다. 설계 리비전 일치와 도메인별 검증 범위 판정은 선택된 계획의 모든
필수 도메인에 그대로 적용된다.
