# 단일 작업 RTL 컨테이너 워커

서비스의 `/analysis/rtl-signoff`와 스트리밍 API에서 컨테이너 실행을 선택할 수 있습니다.
기본 `SIGNOFF_RTL_EXECUTION=local`은 기존 직접 실행입니다. 컨테이너 모드에서도 인증·인가,
동시 실행 슬롯, 결과와 실행 근거의 저장은 API 서버가 담당합니다.

## 서비스 연결

이미지를 빌드한 뒤 백엔드 실행 환경에 다음 값을 지정합니다.

```sh
SIGNOFF_RTL_EXECUTION=container
SIGNOFF_RTL_WORKER_IMAGE=signoff-rtl-worker:local
```

API 프로세스가 Docker CLI와 데몬에 접근할 수 있어야 합니다. 요청마다 로컬 이미지의 불변
ID를 조회하고 그 ID로 실행합니다. 실행 요청 중 이미지를 내려받지 않으며, 이미지나 Docker가
없어도 직접 실행으로 대체하지 않습니다. 성공한 실행 근거에는 컨테이너 방식과 이미지 ID를 기록합니다.

컨테이너 모드의 `/ready`는 DB 조회와 함께 Docker의 로컬 이미지 ID 조회를 확인합니다.
이미지 누락이나 Docker 연결 실패는 503입니다. 3초 검사 제한, 5초 내부 캐시와 검사 범위는
[운영 상태 확인](operations.md)에 설명되어 있습니다. `/health`는 워커 장애와 무관한 생존 확인입니다.

전체 작업 마감 시간은 240초이며 입력 전송·진행 수신·프로세스 종료 대기를 포함합니다.
표준 출력은 16 MiB, 표준 오류는 128 KiB까지 읽습니다. 결과 이벤트는 즉시 저장하지 않고
단계 순서·결과 스키마·단계 판정 일치·정상 종료·컨테이너 제거 확인까지 모두 기다립니다.
실패하면 동기 API는 503, 이미 시작한 스트림은 `error` 이벤트를 반환하며 런을 저장하지 않습니다.

스트리밍 연결 종료는 진행 이벤트 대기 중에도 취소 신호를 전달합니다. 최종 결과 전 취소나
마감 시간 초과 시 Docker CLI를 종료하고 해당 작업 이름의 컨테이너만 강제 제거합니다.
자동 제거와 경합할 수 있으므로 inspect로 부재를 확인하며, 정리 확인에 추가로 최대 10초를 사용합니다.
정리가 확인되지 않으면 결과를 전달하지 않고 작업 컨테이너 이름을 서버 오류 로그에 남깁니다.
동기 요청은 클라이언트 연결 종료만으로 취소되지 않을 수 있습니다. 또한 완료 결과의 DB 커밋
이후 응답이 유실된 경우에는 기록이 남을 수 있으므로 다시 실행하기 전에 프로젝트 이력을 확인하세요.

워커 내부에도 독립적인 300초 마감 시간이 있습니다. 컨테이너 PID 1의 감독 프로세스가
별도 분석 프로세스를 실행하므로, 호스트 API나 Docker 클라이언트가 사라져도 제한 시간에
종료 코드 124로 종료합니다. 입력 EOF를 기다리는 시간도 포함하며, 작업이 먼저 끝나면
타이머를 해제하고 작업의 종료 코드를 그대로 반환합니다. 시간 초과는 완료 결과로 처리되지 않습니다.

감독 프로세스가 종료되면 같은 PID 네임스페이스의 나머지 프로세스도 Linux 커널이 종료합니다.
이는 [Linux PID 네임스페이스 동작](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)에
따른 것이며, Docker 데몬이 정상 동작하는 경우 `--rm`으로 컨테이너도 제거됩니다.
API는 내부 제한을 300초로 고정합니다. 워커를 직접 검증할 때는 컨테이너 환경의
`SIGNOFF_RTL_WORKER_DEADLINE_SECONDS`로 1–300초를 지정할 수 있습니다. 요청 본문으로 변경할 수 없습니다.

데몬 장애·컨테이너 정지·커널 장애에서는 시간 제한 및 제거 보장이 끊길 수 있습니다.
아래 정리기는 데몬이 응답할 때 만료된 컨테이너를 수거합니다. 분산 작업 큐는 아직 없습니다.

## 장애 후 남은 컨테이너 정리

새 작업은 서비스 식별자 `signoff.rtl-owner`와 최대 생존 시간
`signoff.rtl-lease-seconds=360`을 함께 기록합니다. 기본 식별자는 호스트 이름과 백엔드
경로의 해시입니다. 여러 API 인스턴스가 같은 배포를 담당하면
`SIGNOFF_RTL_WORKER_OWNER`에 동일하고 고유한 값을 지정하세요. 배포 간에는 값을 공유하지 않습니다.
기존 작업을 수거하려면 작업을 생성할 때 사용한 식별자가 유지되어야 합니다.

```sh
# backend 디렉터리에서, 서버와 같은 Docker 연결 및 owner 설정으로 실행
.venv/bin/python -m app.worker_maintenance             # 미리보기
.venv/bin/python -m app.worker_maintenance --apply --limit 25
# 같은 목록을 최대 10회에 나눠 처리 (각 회차 JSON 한 줄 출력)
.venv/bin/python -m app.worker_maintenance --apply --limit 25 --passes 10
# 자동 정리와 같은 저장된 목록을 이어서 처리
.venv/bin/python -m app.worker_maintenance --apply --resume --passes 10
```

정리기는 Docker 데몬의 시각과 생성 시각을 비교합니다. worker·owner·생존 시간 라벨,
작업 이름 형식과 전체 컨테이너 ID가 모두 맞고 생성 후 360초 이상인 작업만 대상입니다.
제거 직전에 다시 검사하고 불변 ID로 제거하므로 이름이 재사용된 새 작업을 대상으로 삼지 않습니다.
일시 정지된 만료 작업도 제거하며, 라벨이 없는 이전 버전 작업·다른 배포·만료 전 작업은 보존합니다.
시각 기준은 데몬의 벽시계이므로 운영 중 큰 시각 변경에는 주의가 필요합니다.

`SIGNOFF_RTL_EXECUTION=container`와 `SIGNOFF_RTL_REAPER_ENABLED=1`을 함께 지정하면
API 시작 시와 각 검사 종료 60초 후에 자동 정리합니다. 기본값은 비활성입니다.
처음에 해당 배포의 컨테이너 ID 목록을 확보하고 검사당 최대 100개, 제거 기본 25개
(명령에서 1–100 지정)를 처리합니다. 자동 정리는 남은 ID를 디스크에 저장하여 다음 주기에
이어 검사합니다. 현재 목록을 끝낸 다음 새 목록을 확보하므로 새 작업이 오래된 작업을 밀어내지 않습니다.
검사 사이에 사라진 컨테이너는 건너뜁니다. 검사/제거 오류가 난 ID는 현재 목록에서 제외하고
오류를 보고합니다. 나머지 목록을 끝내고 새 목록을 확보하면 Docker에 남아 있는 실패 작업도
다시 검사합니다. 실패 ID 하나가 새 작업 발견을 계속 막지 않으며, 실패를 제거 성공으로 기록하지 않습니다.
종료 신호나 시간 예산 때문에 제거를 시작하지 못한 작업은 현재 목록에 보존합니다.
API 재시작 시 마지막으로 저장한 목록을 복원합니다. 완료 전 강제 종료된 회차는 일부를 다시
검사할 수 있으며, 매번 실제 Docker 메타데이터를 재검사하므로 저장된 ID만으로 제거하지 않습니다.
검사 시간 예산은 20초이며 진행 중인 Docker 호출의 제한 시간만큼 더 걸릴 수 있습니다.
출력의 `remaining`은 확보한 목록에서 남은 ID 수이며 `scan_truncated`가 참이면 순회가 남아 있습니다.
CLI는 기본 한 회차만 실행합니다. `--passes 1–100`으로 같은 목록을 이어 처리할 수 있으며,
목록을 끝내면 지정한 회차 수보다 일찍 종료합니다. 일반 CLI는 별도 목록을 사용하며,
`--apply --resume`은 자동 정리의 저장 상태를 공유합니다. 미리보기는 자동 정리 위치를 바꾸지 않습니다.
목록은 최대 10,000개로 제한하며 초과하면 명시적으로 실패하고 그 회차에 아무것도 제거하지 않습니다.
배포를 분리하거나 운영자가 목록을 점검해야 합니다. 지속적인 Docker 오류와 회차를 완료하기 전의
반복적인 강제 종료는 순회를 지연할 수 있습니다. 분산 큐는 후속 범위입니다.

### 정리 상태 저장소

기본 저장 위치는 `backend/.rtl-reaper`이며 `SIGNOFF_RTL_REAPER_STATE_DIR`로 변경합니다.
운영에서는 재배포 후에도 유지되는 로컬 볼륨을 지정하세요. 같은 호스트의 API 프로세스와
`--resume` CLI는 동일한 디렉터리·owner·Docker 데몬을 사용해야 합니다.
디렉터리는 실행 계정 소유의 0700, 파일은 0600이며 Git과 자기 개선 작업 사본에서 제외됩니다.
별도 경로를 지정한 경우 그 경로도 소스 저장소 밖에 두세요.

상태 파일은 owner와 Docker 데몬 ID별로 구분하고 ID 목록만 저장합니다. 소스·환경 변수·DB는
저장하지 않습니다. 파일 잠금을 잡은 프로세스만 회차를 진행하며, 다른 자동 정리 프로세스는
다음 주기에 재시도합니다. `--resume` CLI의 잠금 충돌은 종료 코드 1로 알려 줍니다.
프로세스 종료 시 커널이 잠금을 해제합니다. 이 잠금은 같은 호스트의 파일 시스템을 전제로 하며
NFS나 여러 호스트 사이의 분산 잠금은 검증하지 않았습니다.

임시 파일에 기록하고 파일 동기화·원자적 교체·디렉터리 동기화로 상태를 저장합니다.
쓰기 불가 시 컨테이너 변경 전에 실패합니다. 변경 후 저장에 실패하면 이전 상태로 다시 검사할 수 있습니다.
손상·버전/범위 불일치·중복 ID 상태는 경고를 남기고 새 목록을 확보합니다. 심볼릭 링크,
다른 소유자 또는 공개 권한의 파일은 사용하지 않습니다. 저장소 자체의 백업/복구는 별도 운영 범위입니다.

[Docker의 before 필터](https://docs.docker.com/reference/cli/docker/container/ls/#before)는
기준 컨테이너의 ID 또는 이름에 의존합니다. 수거 중 그 컨테이너가 삭제될 수 있어 이 정리기는
삭제 가능한 페이지 기준 대신 확보한 ID 목록을 사용합니다.

Docker 오류는 제거 성공으로 간주하지 않으며 자동 정리는 오류 종류를 로그에 남기고 다음 주기에
재시도합니다. 데몬/커널 자체의 복구는 수행하지 않습니다. DB 실행 기록은 변경하지 않습니다.

## 빌드와 검증

저장소 루트에서 실행합니다.

```sh
docker build -f backend/Dockerfile.rtl-worker -t signoff-rtl-worker:local backend
python3 scripts/check_rtl_worker.py
backend/.venv/bin/python scripts/check_rtl_worker_api.py
backend/.venv/bin/python scripts/check_rtl_worker_deadline.py
backend/.venv/bin/python scripts/check_worker_reconciliation.py
```

검증 스크립트는 호스트 디렉터리와 DB를 마운트하지 않습니다. 매 작업마다 새 컨테이너를
사용하며 표준 입력에 한 개의 JSON을 전달합니다. 실행 후 자신의 컨테이너만 제거합니다.

- UID/GID 65534, 읽기 전용 루트, 모든 capability 제거, no-new-privileges.
- 네트워크 없음, CPU 1개, 전체 메모리·스왑 합계 1 GiB, 최대 프로세스 64개.
- 쓰기 공간은 `/tmp`의 128 MiB tmpfs이며 실행·장치·setuid를 허용하지 않습니다.
- 툴별 CPU·파일 크기·주소 공간 제한도 그대로 적용됩니다.

이 제한은 Docker **실행 옵션**으로 적용됩니다. 이미지를 옵션 없이 실행하면 같은 격리 조건을
보장하지 않습니다. API의 컨테이너 모드는 위 제한을 자체 적용합니다.
Docker 데몬 접근 권한은 호스트 권한 경계이며, 이미지 신뢰·런타임 보안
검토·작업 큐·대규모 장애 복구는 별도로 다뤄야 합니다.
옵션의 의미는 [Docker 실행 문서](https://docs.docker.com/reference/cli/docker/container/run/)를 참고하세요.

## 입력과 출력

표준 입력을 닫으면 워커가 요청을 읽습니다. 입력은 UTF-8 JSON이며 최대 16 MiB입니다.

```json
{"protocol":"signoff/rtl-worker/v1","request":{"code":"module top; endmodule"}}
```

`request`는 기존 RTL 검증 규칙을 사용하는 `code`, `testbench`, `testbench_top`만 받습니다.
테스트벤치와 top은 함께 전달해야 합니다. 프로젝트 ID, DB 경로, 실행 옵션은 받지 않습니다.
중복 JSON 필드·잘못된 프로토콜·잘못된 요청·입력 한도 초과는 실행 전에 거절합니다.

출력은 한 줄에 하나의 JSON(NDJSON)입니다. 각 이벤트에는 같은 `protocol`이 포함됩니다.
`stage_start`, `stage_done` 이벤트 후 마지막 `result`로 기존 사인오프 결과를 반환합니다.
전체 출력은 오류 이벤트 공간을 포함해 16 MiB로 제한합니다. 최종 결과가 없거나 실행 오류가
발생하면 종료 코드 1입니다. 요청 오류는 종료 코드 2이고 표준 오류에 일반 메시지만 출력합니다.
호출자는 **최종 결과와 정상 종료를 모두 확인**해야 하며 중간 이벤트만으로 결과를 저장하면 안 됩니다.

시뮬레이션은 기본 비활성입니다. 운영자가 컨테이너에 `SIGNOFF_SIMULATION_MODE=trusted_local`을
지정한 경우에만 실행됩니다. 요청 본문에서 이 정책을 변경할 수 없습니다.

## 검증 범위

Linux ARM64의 실제 Verilator·Yosys·Icarus에서 단계 순서·정상 결과·실패 테스트벤치·
시뮬레이션 비활성·잘못된 작업 거절을 확인합니다. 같은 실행 옵션으로 비관리자 UID,
권한 상승 차단, capability 제거, 읽기 전용 루트, 앱 DB 부재, 외부 연결 실패도 검사합니다.
이는 운영 보안 검토나 모든 컨테이너 탈출 가능성에 대한 증명이 아닙니다.

API 통합 검사는 별도 임시 DB에서 동기·스트림 저장과 이미지 ID 보존, 이미지 누락 시 저장 거절,
취소·시간 초과 후 컨테이너 제거를 검증합니다. 실제 HTTP 서버에서도 시뮬레이션 진행 중 연결
종료 후 컨테이너 제거와 런 비저장을 확인했습니다. 브라우저에서는 컨테이너 기반 정상/실패
시뮬레이션, 근거 다운로드·이미지 표시와 워커 오류 후 실행 버튼 복구를 검사했습니다.

독립 시간 제한 검사는 짧은 테스트 제한으로 실제 `vvp`의 실행을 확인한 뒤 호스트 Docker
클라이언트를 SIGKILL로 종료합니다. 그 직후 컨테이너가 실행 중임을 확인하고, 호스트에서
제거 명령을 내리기 전에 워커가 스스로 종료되어 컨테이너가 사라지는지 검사합니다.
별도로 종료 코드 124와 최종 결과 부재, 입력 대기 중 만료, 정상 종료 시 타이머 해제,
분석 프로세스의 실패 코드 보존을 검증합니다.

정리 통합 검사는 별도 owner를 가진 실제 Docker 컨테이너를 만들고 가상 만료 기준 시각을
주입합니다. 미리보기의 비변경, 만료된 일시 정지 작업 제거, 새 작업·다른 owner·이전 라벨
작업 보존을 검사한 뒤 자신이 만든 컨테이너를 제거합니다. 실제 360초 대기를 검증하는 검사는 아닙니다.
동일 검사에서 회차당 검사량을 2개로 낮춰 여러 회차 뒤의 오래된 작업까지 실제 제거되는지 확인합니다.
회귀 테스트에서는 100개보다 많은 목록, 새 작업 유입, ID 소멸, 제거 한도, 오류 재시도와 CLI 연속 처리를 검사합니다.
Docker 검사의 각 회차는 새 Python 프로세스에서 실행하여 디스크 상태 복원을 확인합니다.
별도 회귀에서는 강제 프로세스 종료 후 상태/잠금 복구, 프로세스 간 잠금 충돌, 원자적 교체 실패,
손상·과대·잘못된 범위의 상태와 심볼릭 링크 거절, 쓰기 실패 시 컨테이너 변경 방지를 검사합니다.

## RTL 도구 실행 기록

새 워커 결과의 `tool_runs`는 `lint`(기본 Verilator), `width`(폭 경고를 포함한 Verilator),
`synthesize`(Yosys)의 `command` 인수 배열·`exit_code`·`error`·`log`를 보존한다.
명령은 임시 작업 폴더의 `design.sv`를 참조하며 서버의 고정 자원 제한 런처를 거쳐 실행된다.
로그는 stdout/stderr를 합친 UTF-8 텍스트이며 도구별 최대 128 KiB다. 한도를 초과하면
도구 실행을 중단하고 오류를 기록한다. 잘못된 UTF-8은 대체되므로 원시 바이트 사본은 아니다.
별도 버전 명령을 추가 실행하지 않는다. 도구가 로그에 출력한 버전만 로그에 남으며 컨테이너
이미지 ID는 호스트가 확인한 실행 환경 식별자로 별도 보관한다.

실행 근거 보기에서 명령과 로그를 접어 확인하고 근거 JSON에 함께 내려받을 수 있다.
명령 인수는 텍스트로만 표시하며 재실행 버튼이나 AI 호출을 만들지 않는다. 시뮬레이션의
컴파일/실행 로그는 기존 시뮬레이션 근거에 남는다. 미실행 도구는 null이고 기존 워커/이전
결과에는 필드가 없을 수 있어 미보관으로 표시한다. 기존 워커 결과도 계속 받을 수 있지만
새 기록을 생성하려면 워커 이미지를 새 코드로 빌드해야 한다. 기존 결과를 소급 생성하지 않는다.

현재 워커 Yosys의 `Number of cells: N` 및 `CELL N` 형식과 새 버전의 `N cells`,
`N CELL` 형식을 모두 읽는다. 단일 모듈 실제 fixture의 플립플롭 4개와 래치 0개를
확인했다. 통계는 일반 합성 결과로 물리적 면적·타이밍이나 전체 칩 검증을 의미하지 않는다.
복잡한 계층 통계 및 라이브러리 셀 분류는 추가 검증이 필요하다.

## 린트·합성 최상위 모듈 선택

RTL 래더의 선택 입력 `top_module`은 Verilator 기본/폭 검사와 Yosys hierarchy에 동일하게
전달된다. 120자 이하 영문자/밑줄로 시작하는 단순 식별자이며 나머지에는 영문자·숫자·
밑줄·$만 허용한다. 공백·경로·명령 구분자·escaped identifier는 지원하지 않는다. API는
잘못된 형식을 실행 전에 422로 거절하고, 유효한 이름이지만 설계에 없으면 실제 도구 실패를
기록한다. 도구가 없으면 기존처럼 미실행 상태로 남으며 존재 여부를 추측하지 않는다.

생략/null은 기존의 첫 모듈 선언 선택을 유지한다. 이는 자동 계층 루트 추론이 아니다.
`top_module_requested`는 지정된 이름 또는 null로 결과·실행 근거·JSON에 저장되고, `module`은
선택한 분석 대상 이름이다. 소스 해시는 입력 바이트만 나타내므로 같은 입력에 다른 top을
지정해도 같다. 재현 시 소스와 선택 값, 명령 기록을 함께 확인한다.

정적 설계 규칙은 계속 전체 단일 파일을 검사하며, 시뮬레이션은 별도의 `testbench_top`을
사용한다. top 선택만으로 테스트벤치가 그 설계를 검증했다고 증명하지 않는다. 계층 전체
셀 수 집계와 라이브러리별 분류는 여전히 추가 검증 대상이다.

컨테이너 요청에도 같은 값을 전달하며 결과의 선택 값/대상이 요청과 다르면 저장 전에
거절한다. 이 검사는 컨테이너 정리 이후에 수행한다. 새 top 입력을 지원하려면 워커 이미지를
함께 갱신해야 한다. 이전 워커는 명시적 top 입력을 무시하고 실행하지 않고 실패로 처리된다.
