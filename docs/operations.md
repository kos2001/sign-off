# 운영 상태 확인과 요청 추적

## 생존 상태와 준비 상태

- `GET /health`: HTTP 프로세스가 응답하는지 확인합니다. DB에 접속하지 않습니다.
- `GET /ready`: DB 연결과 모든 앱 모델 테이블의 필수 열에 대한 SELECT가 가능한지 확인합니다.
  각 테이블에 `LIMIT 0`을 적용하므로 설계·보고서·계정 데이터 행은 읽지 않습니다.
  테이블 또는 필수 열 누락은 준비 실패이며, 이후 복구되면 다음 요청에 반영됩니다.
  `SIGNOFF_RTL_EXECUTION=container`에서는 Docker 데몬에 연결하여 설정한 로컬 워커 이미지의
  ID도 조회합니다. 이미지 누락·Docker 연결 실패·잘못된 실행 설정이면 준비 실패입니다.
  정상은 HTTP 200 `{"status":"ready"}`, 실패는 HTTP 503 `{"status":"not_ready"}`입니다.
  실패 응답에 `Retry-After: 5`를 포함하고 모든 준비 상태 응답은 `Cache-Control: no-store`입니다.

두 경로 모두 로그인 없이 호출할 수 있으며 DB 주소·계정·스키마 상세나 오류 원문을 반환하지
않습니다. 개발 프런트엔드 프록시에서는 `/api/health`, `/api/ready`로 접근합니다.

Docker 확인은 이미지를 내려받거나 작업 컨테이너를 실행하지 않습니다. 최대 3초를 기다리고
성공·실패 결과를 각 API 프로세스에서 5초간 재사용합니다. HTTP 응답의 캐시 금지와 별개의 내부 캐시이며,
장애/복구 감지에 최대 5초의 지연이 있을 수 있습니다. 이미지와 Docker 연결 환경 설정이 바뀌면
즉시 다시 확인합니다. Docker CLI 설정 파일 내용 변경은 다음 캐시 만료 때 반영됩니다.
유효한 캐시가 없고 다른 요청이 검사 중이면 추가 Docker 호출이나 대기 없이 503을 반환합니다.
모니터링에서는 한 번의 실패로 즉시 재시작하지 않도록 연속 실패 기준을 설정하세요.

준비 상태는 필수 테이블·열의 SELECT 가능 여부와 컨테이너 모드의 이미지 조회 가능 여부입니다.
열의 타입·제약 조건·인덱스 일치, 쓰기 권한, 전체 스키마 마이그레이션의 정확성,
실제 컨테이너 생성 권한·이미지 내부 툴·정리기 저장소·검토 제공자·RTL 실행 슬롯의 여유·기능적 정확성은 검사하지 않습니다.
`local` 모드에서는 Docker나 로컬 EDA 툴을 확인하지 않습니다.
DB 드라이버/연결 풀의 대기 시간은 그대로 적용됩니다. 운영 모니터링의 요청 타임아웃과
실패 임계값은 배포 환경에 맞게 별도로 설정하세요. 이 변경은 실제 배포나 자동 재시작 정책을
구성하지 않습니다.

## 문의 번호와 로그

서버가 모든 HTTP 요청에 무작위 `X-Request-ID` 응답 헤더를 생성합니다. 클라이언트가 전달한
같은 이름의 헤더는 신뢰하지 않습니다. 서버 내부 예외가 응답 헤더 전송 전에 발생하면
HTTP 500과 일반 오류 메시지, 같은 `request_id`를 반환하고 캐시를 금지합니다.

브라우저는 일반 API 요청과 RTL 스트리밍 시작 요청의 5xx 오류에 문의 번호를 표시합니다.
요청 번호는 권한이나 인증 수단이 아니며 관리자에게 로그 조회를 요청할 때 사용합니다.
최종 응답 이전의 오류가 항상 DB 롤백을 의미하지는 않습니다. 결과 저장 여부를 확인하고
재시도하세요. 가져오기 API는 같은 import_id로 재시도할 수 있습니다.

Uvicorn 기본 INFO 로그에서 `uvicorn.error.signoff` 네임스페이스의 기록을 확인합니다.

- `response_headers`: request_id, HTTP method, 등록된 route 형식, status, elapsed_ms.
- `request_failed`: 응답 헤더 전송 전 예외의 request_id와 예외 클래스.
- `readiness_failed`: DB 또는 워커 준비 상태 조회 실패의 request_id, component (`database` 또는 `rtl_worker`)와 예외 클래스.
  테이블·열 이름, 연결 정보, 예외 원문은 포함하지 않습니다.

`elapsed_ms`는 응답 헤더가 준비되기까지의 시간입니다. NDJSON 전체 분석이나 다운로드의
총 수행 시간이 아닙니다. 이 애플리케이션 기록에는 요청 본문·쿠키·인증 헤더·쿼리 문자열·
예외 원문을 넣지 않습니다. 등록되지 않은 경로는 `unmatched`로 기록합니다.
리버스 프록시·Uvicorn 기본 access log·DB 드라이버·외부 라이브러리의 별도 로그 정책까지
이 설정이 바꾸지는 않습니다. 로그 수집·보관·알림은 운영 환경에서 별도로 구성합니다.

## Prometheus 운영 지표

공백 없는 출력 가능 ASCII 32~256자의 `SIGNOFF_METRICS_TOKEN`을 secret manager에서 주입하면 `GET /metrics`가
Prometheus text exposition 형식을 제공합니다. 토큰이 없으면 경로는 404로 숨겨지고, 잘못된 설정은
API 시작을 거부합니다. 수집기는 `Authorization: Bearer <token>`을 보내야 하며 실패 응답과 성공
응답 모두 캐시하지 않습니다. 이 토큰은 로그인 세션이나 일반 API 토큰을 대신하지 않습니다.

```yaml
scrape_configs:
  - job_name: signoff-api
    authorization:
      credentials_file: /run/secrets/signoff_metrics_token
    static_configs:
      - targets: [signoff-api:8000]
```

제공 지표는 프로세스 시작 시각, 진행 중 요청 수, HTTP 요청 수, 응답 헤더까지 걸린 시간 히스토그램,
준비 상태 검사 결과입니다. HTTP 라벨은 제한된 method, 등록된 route 템플릿, 상태 코드 등급만
포함합니다. 프로젝트 ID, 쿼리 문자열, 인증값, 오류 원문은 포함하지 않습니다. 준비 실패 component는
`database` 또는 `rtl_worker`로만 구분합니다. 다음 조건을 초기 알림 기준으로 권장합니다.

- `/ready` 연속 실패 또는 `signoff_readiness_checks_total{result="not_ready"}` 증가
- 5xx 비율의 지속 상승
- route별 응답 시간 p95가 서비스 목표를 지속적으로 초과

지표는 각 API 프로세스 메모리에만 존재하며 재시작 시 초기화됩니다. 여러 Uvicorn worker나 여러
인스턴스에서는 각 대상을 직접 scrape한 뒤 Prometheus에서 합산하세요. 로드 밸런서 한 주소만
scrape하면 일부 프로세스 지표를 놓칠 수 있습니다. 장기 보관과 알림 규칙은 Prometheus 등 외부
시스템에서 구성합니다.

이미 시작된 스트리밍 응답의 상태 코드를 나중에 500으로 바꿀 수는 없습니다. 현재 클라이언트는
최종 result 이벤트가 없는 종료를 분석 완료로 간주하지 않습니다. 스트림 전체에 걸친 분산 추적과
실행 작업 ID 기반 추적은 아직 구현하지 않았습니다.

## 검증

`backend/tests/test_operations.py`는 요청 번호 생성, DB 장애, 각 앱 테이블 및 필수 열 누락의 503과 복구 후 200, 데이터 행 없는 조회,
인증 모드에서도 공개 상태 조회, 지표 인증·경로 라벨·민감 정보 비노출, 민감한 예외·쿼리·헤더가 애플리케이션 로그/오류에 없는지 검사합니다.
기존 커밋 실패 테스트도 500 응답과 함께 비밀번호·세션·위반·권한·보고서 저장 롤백을 확인합니다.

`backend/tests/test_worker_readiness.py`는 이미지/데몬 오류·3초 제한 설정·캐시 만료와 복구·
설정 변경·동시 호출·민감한 오류 비노출을 검사합니다. 실제 Docker 확인은
`backend/.venv/bin/python scripts/check_worker_readiness.py`로 실행합니다. 임시 DB에서
없는 이미지·접속 불가능한 소켓의 503, 정상 이미지의 200, 복구 및 생존 상태 유지를 확인하며
사용 중인 서버 설정이나 작업 컨테이너는 변경하지 않습니다.

`scripts/browser_request_errors_check.mjs`는 API 오류 응답을 모의하여 문의 번호 표시,
내부 메시지 비노출, 연결 재시도, RTL 입력 유지와 모바일 화면을 읽기 전용으로 확인합니다.
실제 운영 장애 조치나 외부 로그 수집 시스템은 검증 범위에 포함하지 않습니다.

## 브라우저 화면 오류 복구

등록되지 않은 SPA 주소에는 없는 페이지 안내와 대시보드 링크를 표시한다. 이는 클라이언트
화면 처리이며 프런트엔드 서버의 HTTP 상태 코드를 404로 바꾸지는 않는다. 인증이 필요한
환경에서는 기존 로그인 절차를 먼저 거친다. 주소·쿼리 원문을 안내 화면에 표시하지 않는다.

페이지 렌더링/생명주기 오류는 경로별 경계에서 처리하여 사이드바·인증·메모리 검토 초안을
유지한다. 다른 경로로 이동하면 오류 경계를 초기화하지만, 정상 화면의 검색/필터 이동마다
페이지를 강제로 재마운트하지 않는다. 공통 영역/인증 제공자의 렌더링 오류는 바깥 경계에서
일반 복구 화면을 표시한다. 예외 원문과 스택은 사용자 화면에 표시하지 않는다.

새로 고침은 브라우저 전체를 다시 로드하므로 저장하지 않은 입력은 사라질 수 있다. 공통
영역 오류로 제공자 자체가 해제된 경우에도 초안 보존을 보장하지 않는다. 화면 오류는 이미
보낸 저장·승인 요청을 취소하거나 롤백하지 않으므로 처리 이력을 확인한 뒤 재요청한다.
복구 UI는 분석/저장 요청을 직접 재전송하지 않으며, 다시 방문한 화면은 기존 초기화 규칙을
따른다. 프로젝트 화면의 조건부 자동 AI 검토도 기존 동작을 따른다.

API·이벤트 핸들러·비동기 작업 오류는 기존 개별 UI에서 처리한다. 이 경계는 JS 번들 로드
실패, 브라우저 프로세스 종료, 외부 오류 수집/알림까지 해결하지 않는다.
`scripts/browser_screen_recovery_check.mjs`는 임시 인증 DB와 모의 불완전 API 응답으로
없는 주소·페이지/공통 오류·링크/새로 고침 복구·검토 사유 보존·비노출·320/390/1440px를 확인한다.
