# 계정 인증과 프로젝트 접근 권한

## 실행 모드

- `SIGNOFF_AUTH_MODE=local` (기본): 기존 단일 사용자 데모 동작. 계정 인증 없이 접근하며
  화면에 **로컬 모드 · 계정 인증 없음**을 표시합니다. 신뢰된 로컬 개발 용도입니다.
- `SIGNOFF_AUTH_MODE=required`: 로그인이 필요한 모드. `/health`, 로그인·세션 확인을 제외한
  프로젝트·런·위반·분석·에이전트 API에 인증을 적용합니다. 잘못된 모드 값은 시작 오류입니다.

운영에서는 반드시 required 모드와 HTTPS를 함께 사용하고, 인증을 적용하기 전의 서버가
동시에 서비스되지 않도록 모든 워커를 교체해야 합니다. 프런트엔드와 `/api`는 같은 origin으로
제공합니다. 외부 CORS 허용은 포함하지 않습니다.

## 초기 관리자와 계정 생성

실제 서비스 DB를 가리키는 `SIGNOFF_DATABASE_URL`을 설정한 백엔드 디렉터리에서:

```sh
cd backend
.venv/bin/python -m app.accounts create-user admin --admin
.venv/bin/python -m app.accounts create-user designer
.venv/bin/python -m app.accounts grant designer 1 editor
SIGNOFF_AUTH_MODE=required .venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
```

비밀번호는 터미널의 숨김 입력으로 두 번 받습니다. 15–256자를 허용하며 명령행 인자나
환경변수로 전달하지 않습니다. 계정 이름은 소문자 영문·숫자·`_ . -`를 사용하는 최대 64자이고
첫 글자는 영문 또는 숫자입니다. 사용자 이름 변경·삭제는 제공하지 않아 이력의 계정 식별을 유지합니다.
계정 공개 가입은 없습니다. 관리자 계정은 모든 프로젝트를 조회·관리할 수 있습니다.
기존 프로젝트에는 관리자가 CLI 또는 구성원 화면에서 소유자를 지정합니다.

HTTPS용 세션 쿠키가 기본입니다. HTTP localhost에서만 검증할 경우 서버에
`SIGNOFF_COOKIE_SECURE=false`를 명시합니다. 이 옵션은 운영 HTTPS에서 사용하지 않습니다.

## 로그인한 계정의 비밀번호 변경

로그인 후 메뉴의 **계정 설정**에서 현재 비밀번호와 새 비밀번호를 입력합니다.
새 비밀번호는 현재와 달라야 하며 15–256자입니다. 변경 성공 시 현재 브라우저의 세션 쿠키와
CSRF 토큰을 교체하고 다른 모든 세션은 폐기합니다. 다른 기기에서는 다음 요청부터 재로그인이
필요합니다. 기본 local 모드에서는 계정 설정 기능을 사용하지 않습니다.

`POST /auth/password`는 `current_password`, `new_password`와 현재 세션의 CSRF 헤더를 받습니다.
현재 비밀번호 오류는 400, 인증 없음은 401, CSRF 오류는 403, 입력 형식 오류는 422입니다.
계정당 5분에 8회까지 시도할 수 있으며 초과하면 429를 반환합니다.
검증 도중 운영자가 비밀번호를 재설정하거나 계정을 비활성화하면 409로 변경을 거부합니다.
비밀번호·세션 교체는 한 트랜잭션이며 저장 실패 시 기존 비밀번호와 세션을 유지합니다.
인증 API의 입력 검증 오류는 입력 비밀번호를 응답에 포함하지 않습니다.

두 브라우저의 세션 종료, 오류 표시, CSRF 교체 후 로그아웃, 새 비밀번호 재로그인과 모바일
화면은 `scripts/browser_password_check.mjs`로 확인합니다. 위 seed로 생성한 새 테스트 DB와
`SIGNOFF_AUTH_FIXTURE`, `SIGNOFF_TEST_UI=http://127.0.0.1:15174`를 지정합니다.
이 검증은 QA 비밀번호를 바꾸므로 실행 후 테스트 DB와 자격증명 파일을 폐기합니다.

## 프로젝트 역할

| 역할 | 권한 |
| --- | --- |
| viewer · 열람자 | 프로젝트, 런, 위반, 이력, 실행 근거, 비교와 게이트 조회 |
| editor · 편집자 | 위 권한 + 런 등록/수정, 수동 위반 등록, 수정 완료 처리 및 수정 완료 항목 재오픈, 프로젝트에 RTL 실행 기록 |
| approver · 승인자 | 위 권한 + 웨이버 승인·해제 |
| owner · 소유자 | 위 권한 + 구성원 추가·역할 변경·제거 |

로그인한 사용자는 프로젝트를 생성할 수 있고 생성한 프로젝트의 소유자가 됩니다.
로그인한 모든 사용자는 프로젝트에 저장하지 않는 임시 분석과 제출한 결과의 에이전트 검토를
실행할 수 있습니다. 에이전트 대화 ID는 계정별로 분리됩니다.

구성원은 프로젝트의 **접근 권한** 화면에서 관리합니다. 존재하는 계정 이름과 역할을 입력합니다.
비관리자 소유자는 자신의 권한을 낮추거나 제거할 수 없습니다.
구성원이 아닌 프로젝트는 목록에 나오지 않으며 ID 직접 접근도 404를 반환합니다.
역할이 부족한 변경 요청은 403입니다. 권한 변경은 다음 서버 요청부터 적용됩니다.
이미 시작한 실행을 강제로 취소하는 기능은 포함하지 않습니다.
브라우저는 새로 고침·포커스 복귀·주기적 세션 확인으로 역할을 갱신하며 계정/역할 변경 시 캐시를 비웁니다.

## 승인 이력과 기존 데이터

인증 모드에서는 API가 받은 `actor`/`approved_by` 문자열 대신 로그인 계정 이름과 계정 ID를 저장합니다.
`ViolationEvent.actor_user_id`, `Waiver.approved_user_id`가 신원 근거입니다.
이전 직접 입력 기록의 ID는 null로 유지하며 계정 이름이 같아도 인증된 기록으로 바꾸지 않습니다.
프런트엔드는 이력에 **로그인 계정 / 직접 입력**을 구분합니다.

앱 초기화는 사용자·세션·구성원·로그인 제한 테이블과 nullable 신원 열을 추가합니다.
기존 프로젝트 데이터와 위반 버전, 검토 이력을 유지합니다. 기존 서버와 신규 서버의 혼합 운영은
인증/권한 검사를 우회하므로 허용하지 않습니다.

## 세션과 요청 보호

비밀번호는 개별 무작위 salt와 PBKDF2-HMAC-SHA256 600,000회로 저장합니다.
근거: [OWASP 비밀번호 저장 안내](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
세션은 32바이트 무작위 토큰이며 DB에는 토큰의 SHA-256만 저장합니다.
쿠키는 HttpOnly, SameSite=Strict, 기본 Secure이고 절대 만료 시간은 12시간입니다.
재로그인은 해당 브라우저 세션을 교체하고 로그아웃은 서버의 세션을 폐기합니다.

변경 요청에는 세션별 `X-CSRF-Token`을 요구합니다. 로그인/로그아웃에는 커스텀
`X-Signoff-Client: 1` 헤더도 사용합니다. 브라우저는 쿠키와 메모리의 CSRF 토큰을 사용하며
localStorage/sessionStorage에 세션이나 비밀번호를 저장하지 않습니다.
인증 모드 API 응답에는 `Cache-Control: no-store`를 적용합니다.
근거: [OWASP 세션 관리 안내](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

로그인은 5분 동안 계정별 8회, 접속 IP별 40회까지 허용하며 성공 시도도 포함합니다.
카운터는 공유 DB에서 갱신하고 초과 시 429를 반환합니다. 다중 워커에서도 같은 카운터를 사용합니다.
프록시 배포 시 신뢰할 프록시와 클라이언트 IP 전달 설정을 검증해야 합니다.

## 계정 운영 및 복원 후 처리

```sh
.venv/bin/python -m app.accounts reset-password designer
.venv/bin/python -m app.accounts disable-user designer
.venv/bin/python -m app.accounts enable-user designer
.venv/bin/python -m app.accounts revoke-sessions
```

비밀번호 재설정·계정 비활성화는 해당 계정의 세션을 폐기합니다. 재활성화해도 이전 세션은
복구되지 않습니다. 전체 세션 폐기는 운영 점검이나 DB 복원 후 수행합니다.
DB 백업에는 계정 해시, 권한, 세션 테이블도 포함됩니다. **백업을 복원한 DB로 트래픽을 열기 전에**
해당 DB를 가리키도록 환경을 설정하고 `revoke-sessions`를 실행해 과거 세션의 재활성화를 막습니다.

현재 구현은 로컬 계정 기반입니다. SSO/OIDC, MFA, 셀프서비스 비밀번호 복구,
운영자 개인 식별·감사 로그 외부 보관·자동 보존 기간 정책, 조직별 테넌트,
독립적인 보안 검토와 실제 HTTPS 배포 검증은 남아 있습니다.

## 상용 EDA 수집기 자격증명

인증 필수 모드의 자동 수집기는 브라우저 세션과 CSRF 토큰 대신 프로젝트 범위 Bearer 자격증명을
사용할 수 있다. 운영자 CLI `python -m app.collectors`로 발급·목록·폐기하며 평문 토큰은 발급할
때 한 번만 반환한다. 서버는 SHA-256만 저장하고 만료 시각과 폐기 시각을 검사한다.

허용 범위는 해당 프로젝트의 `commercial-sta`, `commercial-cdc`, `commercial-drc`, `commercial-lvs`, `commercial-lec`, `commercial-emir`,
`commercial-dft`, `commercial-power`, `commercial-thermal`, `commercial-rtl` 저장 POST로 고정된다. 미리보기와 모든
조회·검토·승인 API에는 사용할 수 없다. 쿠키와 Bearer 헤더를 함께 보내면 모호한 신원을 허용하지
않고 401로 거부한다. 머신 제출에는 유효한 coverage attestation을 반드시 포함해야 한다. 저장된
evidence에는 자격증명 ID와 이름을 남기며 토큰은 남기지 않는다.
생성 요청과 HMAC 범위 증명 절차는 [상용 EDA 수집기 요청 생성](collector-cli.md)을 참고한다.
RTL trusted_local 실행은 계정 인증과 별개로 OS 샌드박스가 아니므로 다중 사용자 운영용으로 간주하지 않습니다.

## 로그인 세션 관리

**계정 설정 → 로그인 세션**에서 자신의 활성 세션과 만료 시각을 확인하고
**다른 세션 모두 종료**를 실행할 수 있습니다. 현재 세션을 먼저 표시하며 25개씩 이동합니다.
만료된 세션과 다른 계정의 세션은 표시하지 않습니다. 기기 이름·위치·IP 주소를 수집하거나
추정하지 않습니다. 목록은 60초마다 갱신되고 창으로 돌아올 때도 갱신합니다.

- `GET /auth/sessions?offset=0&limit=25`: 본인의 활성 세션만 반환합니다. limit은 1–100.
  공개 항목은 id, current, expires_at(Unix 초)이며 로그인 토큰·토큰 해시·CSRF 비밀은 제외합니다.
- `POST /auth/sessions/revoke-others`: 인증과 CSRF 검증 후 현재 세션을 제외한 본인의
  활성 세션을 종료하고 실제 종료 수 `revoked`를 반환합니다. 현재 쿠키·CSRF는 유지합니다.
- 두 API는 local 모드에서 409, 로그인하지 않은 required 모드에서 401입니다.
  응답은 `Cache-Control: no-store`입니다.

종료된 세션의 다음 인증 요청은 거부됩니다. 이미 실행 중인 요청을 취소하거나 이후 올바른
비밀번호를 사용한 새 로그인을 차단하는 기능은 아닙니다. 로그인·비밀번호 변경과 같은 계정
행 잠금을 사용하고 잠금 후 요청자의 세션을 재확인하여, 동시에 종료된 요청자가 살아 있는
세션을 다시 종료하지 못하게 합니다. 저장 실패 시 종료 작업도 롤백합니다.

`backend/tests/test_session_management.py`는 계정 범위·만료·페이지·비밀 비노출·CSRF,
현재 세션 보존·다른 계정 보존, 중간 세션 종료와 저장 실패를 검증합니다.
`scripts/browser_sessions_check.mjs`는 아래 별도 QA 환경에서 두 로그인과 다른 계정,
실패 후 재시도·새로고침·모바일 화면을 검증합니다. 실제 계정의 세션을 테스트에 쓰지 않습니다.

## 계정 보안 이력

**계정 설정 → 계정 보안 이력**에서 본인 계정의 작업과 로그인 실패를 최신순으로 조회합니다.
`GET /auth/security-events?limit=25&before_id=...`는 1–100개와 다음 커서를 반환하며,
로그인한 본인만 조회할 수 있습니다. 현재 페이지보다 최신인 이벤트가 추가되어도
다음 커서 페이지에 중복되지 않습니다. **최신 이력 보기**로 처음으로 돌아갑니다.

새 `account_security_events` 테이블을 시작 시 추가합니다. 기록 대상은 다음과 같습니다.

- API의 로그인·로그아웃·비밀번호 변경·다른 세션 종료.
- 운영자 CLI의 일반/관리자 계정 생성, 비밀번호 재설정, 비활성화·활성화.
- 운영자 CLI의 전체 세션 종료는 대상 계정이 없는 전역 이벤트 한 건으로 기록합니다.
  본인 계정 이력 API에는 이 전역 이벤트를 노출하지 않습니다.
- 프로젝트 권한 변경은 기존 `project_access_events`에서 별도로 기록합니다.

대상 계정 식별자·이름, 실행 계정 또는 `local operator`, API/운영자 구분, 작업 종류,
종료한 세션 기록 수와 UTC 시각만 저장합니다. 비밀번호·해시·쿠키·CSRF 토큰·요청 본문은
저장하지 않습니다. 비밀번호 교체와 운영자 명령의 종료 수는 만료된 행과 현재 세션도
포함할 수 있습니다. 현재 브라우저용 새 세션을 만든 경우 그 새 세션은 종료 수에 포함하지 않습니다.

실제 변경과 이력을 같은 DB 트랜잭션으로 커밋하므로 이력 저장 실패 시 작업도 롤백합니다.
실패한 비밀번호 변경, 잘못된 CSRF, 기록 기능 추가 이전의 작업은 이력에 포함하지 않습니다.
자동 만료와 로그인 시 이전 쿠키 정리는 별도 종료 이벤트를 만들지 않습니다.

### 로그인 실패 기록

시도 제한을 통과한 요청에서 비밀번호 불일치·계정 없음·비활성 계정 또는 검증 중 계정 변경으로
로그인이 거부되면 `login_failed`를 기록합니다. 응답은 계정 존재 여부와 관계없이 동일한 401입니다.
일치하는 계정은 대상 사용자로만 연결하고 실행자 ID는 null, 실행자 표시는 `unverified client`로
기록합니다. 화면에서는 **인증되지 않은 요청**으로 표시하며 본인이 시도했다고 단정하지 않습니다.

없는 계정 이름도 관리자 검색을 위해 입력된 이름을 보존하지만 대상 사용자 ID는 null입니다.
일반 사용자는 본인 사용자 ID에 연결된 실패만 볼 수 있습니다. 관리자 화면의 **로그인 실패**
필터에서는 등록되지 않았던 이름과 실제 대상 계정을 구분합니다. 비밀번호·토큰·쿠키·IP 주소를
이력에 저장하지 않습니다.

요청 형식·same-origin 헤더 검증 실패와 429 시도 제한 거부는 이 이력에 추가하지 않습니다.
실패 기록도 기존 계정별/IP별 시도 제한 이후에만 쓰며, 제한을 넘긴 반복 요청으로 추가 이력이
늘어나지 않습니다. 이력 저장 실패 시 로그인은 허용되지 않고 500을 반환합니다. 기존 세션을
삭제하거나 새 세션을 만들지 않습니다. 현재 자동 보존 기간 정책과 실패 알림 전송은 없습니다.

이력 변경·삭제 API는 없습니다. DB 직접 접근 권한을 가진 운영자의 변조를 방지하는 저장소나
서명된 감사 로그는 아니며, 운영자 CLI의 개인 신원도 인증하지 않습니다. 현재는 외부 로그
보관·자동 보존 기간 정책은 없습니다. SQLite 백업은 이 테이블도 포함합니다.

`backend/tests/test_account_security.py`는 계정 범위·커서·비밀 비노출·API/CLI 성공 기록과
이력 쓰기 실패 시 세션/비밀번호/이력의 롤백을 검증합니다. 브라우저 세션 검사에도
성공 이력 자동 갱신과 새로고침을 포함합니다.

## 만료된 인증 데이터 정리

로그인 성공 요청은 만료된 세션과 시도 제한 기록을 테이블마다 최대 100개씩 정리합니다.
만료 시각이 오래된 순서로 선택하고, 시각이 같으면 ID 순서를 사용합니다.
두 테이블의 `(expires_at, id)` 인덱스로 만료 범위를 조회하며 별도 정렬을 피합니다.
기존 DB는 서버 시작 시 같은 인덱스를 추가합니다. 첫 인덱스 생성은 테이블 크기에 따라
시작 시간과 쓰기 대기에 영향을 줄 수 있습니다. 정리 명령 자체는 인덱스를 생성하지 않습니다.
오래 쌓인 기록은 백엔드 디렉터리에서 다음 운영 명령으로 별도 정리할 수 있습니다.
기존 `SIGNOFF_DATABASE_URL`이 가리키는 초기화된 DB에 적용되며 스키마를 변경하지 않습니다.

```sh
.venv/bin/python -m app.auth_maintenance --limit 500
.venv/bin/python -m app.auth_maintenance --limit 500 --apply
```

첫 명령은 읽기 전용 미리보기이며, `--apply`를 지정해야 삭제 후 커밋합니다.
`--limit`은 테이블별 1–1000개, 기본 500개입니다. 실행 시작 시각까지 만료된 데이터만
선택하고 삭제 시 만료 조건을 다시 검사합니다. 선택 이후 갱신된 로그인 시도 제한은 보존합니다.
세션과 시도 제한 정리는 같은 트랜잭션이며, 도중 실패하면 둘 다 롤백됩니다.
유효한 세션·활성 시도 제한·계정·프로젝트 권한·보안 이력은 삭제하지 않습니다.

출력 JSON은 기준 시각과 테이블별 개수만 포함하며 세션 토큰이나 계정 정보를 출력하지 않습니다.
`more_at_selection`이 true이면 선택 시점에 처리 한도를 넘는 만료 기록이 있었습니다.
미리보기와 실행 사이에 상태가 달라질 수 있으며, 반복 실행으로 남은 기록을 정리할 수 있습니다.
삭제 행 수를 제한하는 기능이며 조회 시간이나 DB 파일 크기 감소를 보장하지 않습니다.
자동 스케줄링과 SQLite VACUUM은 수행하지 않습니다.

## 관리자 보안 이력 조회

관리자 계정의 **운영 관리 → 보안 이력 관리**(`/admin/security-events`)에서 전체 계정과
전역 작업과 로그인 실패 이력을 조회합니다. 프로젝트 소유자·승인자 권한만으로는 접근할 수 없습니다.
local 모드에서도 이 관리 기능을 활성화하지 않습니다.

`GET /auth/admin/security-events`는 활성 관리자 계정의 세션을 매 요청 확인합니다.
로그인하지 않은 경우 401, 일반 계정은 403, local 모드는 409입니다.

- `subject_username`: 대상 계정 이름 정확히 일치. 생략하면 전역 이벤트도 포함합니다.
  대소문자·접두어·SQL 와일드카드 검색으로 확장하지 않습니다.
- `action`: 지원되는 보안 작업 종류. 모르는 값은 422입니다.
- `source`: `api` 또는 `operator`. 생략하면 모두 조회합니다.
- `created_from`, `created_before`: 시작 시각 포함, 종료 시각 미포함으로 조회합니다.
  UTC `Z` 또는 `+09:00` 같은 시간대가 포함된 시각을 전달해야 합니다.
  서버는 UTC로 변환하며, 시간대 누락·잘못된 시각·시작보다 늦지 않은 종료는 422입니다.
  각 경계는 생략할 수 있습니다.
- `before_id`, `limit`: 본인 이력과 같은 내림차순 커서, 1–100개.

응답에는 기존 이력 필드와 대상 사용자 ID·이름을 추가합니다. 대상이 null인 전체 세션 종료는
화면에서 **전체 계정 (전역 작업)**으로 구분합니다. 쿠키·토큰·비밀번호는 제공하지 않습니다.
검색과 페이지 위치를 URL에 보존하며 조건을 바꾸면 최신 페이지로 돌아갑니다.
기간 입력은 화면에 표시된 브라우저 시간대를 사용합니다. **검색**을 누르면 대상 계정과
기간을 함께 적용하고 UTC 시각을 URL에 보존합니다. 새로고침하면 해당 브라우저의
현지 시각으로 복원합니다. 시작이 종료보다 늦거나 같으면 기존 조회 조건을 유지하고
입력 오류를 표시합니다. **검색 초기화**는 기간과 다른 조건, 페이지 위치를 모두 지웁니다.
조회는 계정이나 이력을 수정하지 않으며 응답은 `Cache-Control: no-store`입니다.

관리 화면 브라우저 검증은 새 DB를 seed할 때 `SIGNOFF_SEED_SECURITY_HISTORY=1`을 지정해
QA 관리자와 합성 보안 이력을 추가한 후 `scripts/browser_admin_security_check.mjs`를 실행합니다.
동일한 `SIGNOFF_AUTH_FIXTURE`·`SIGNOFF_TEST_UI` 변수를 사용합니다. 일반 프로젝트 소유자
접근 차단, 커서·필터·URL 복원·전역 작업·빈 결과·모바일 표시를 검증합니다.

## 재현 가능한 브라우저 검증

아래는 새 임시 DB만 사용합니다. 기존 DB 경로에서는 seed 스크립트가 실행을 거부합니다.

```sh
cd backend
SIGNOFF_DATABASE_URL=sqlite:////private/tmp/signoff-auth-new.db PYTHONPATH=. \
  .venv/bin/python ../scripts/seed_auth_check.py
SIGNOFF_DATABASE_URL=sqlite:////private/tmp/signoff-auth-new.db \
  SIGNOFF_AUTH_MODE=required SIGNOFF_COOKIE_SECURE=false \
  .venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 18000
```

seed가 출력한 JSON 경로는 권한 0600의 임시 QA 자격증명 파일입니다. 별도 터미널에서
프런트엔드를 15173 포트로 실행한 뒤 저장소 루트에서:

```sh
SIGNOFF_AUTH_FIXTURE=/path/printed/by/seed.json \
  node scripts/browser_auth_check.mjs /absolute/path/to/node_modules/playwright/index.mjs
```

QA 계정과 위반 상태를 변경하므로 재실행할 때는 새 DB로 seed합니다.
검증 후 해당 테스트 서버를 종료하고 임시 QA DB·자격증명 파일을 폐기합니다.


## 프로젝트 권한 변경 이력

구성원 화면의 **권한 변경 이력**에서 대상 계정, 이전/변경 후 역할, 처리 계정과 변경 시각을
조회합니다. 소유자 또는 전체 관리자만 조회할 수 있으며, 이전 이력은 커서 기반으로 더 불러옵니다.
API는 `GET /projects/{project_id}/members/history?before_id=...&limit=25`입니다.
`next_before_id`가 null이면 마지막 페이지입니다. `limit`은 1–100입니다.

권한 추가·변경·제거와 이력은 한 트랜잭션으로 저장됩니다. 동시에 같은 구성원을 변경해
조회 당시 역할이 달라졌다면 409를 반환하여 다시 확인하도록 합니다.
변경 전후 역할이 같으면 이력을 추가하지 않습니다. 구성원을 제거해도 이전 이력은 남습니다.
이력 수정·삭제 API는 제공하지 않지만, DB 관리자에 대한 변조 방지 저장소는 아닙니다.

새 프로젝트 생성 시 소유자 부여와 운영 CLI의 `grant`도 기록합니다.
CLI에는 로그인 계정이 없으므로 `source=operator`, `actor_user_id=null`로 구분하며
OS 사용자 이름을 검증된 애플리케이션 신원으로 간주하지 않습니다.
기능 도입 이전의 구성원 이력은 추정하여 만들지 않습니다.
새 테이블 `project_access_events`는 시작 시 생성되며 SQLite 백업에 포함됩니다.
# 데이터베이스 식별자 검증

프로젝트·런·위반·저장 검토·멤버의 경로 ID는 양의 signed 64-bit 범위
(`1`–`9223372036854775807`)로 제한한다. 경로는 1–19자리 ASCII 십진수만 받으며,
RTL 분석 본문의 `project_id`는 정수 또는 `null`만 받는다. 불리언·문자열·소수는
정수로 강제 변환하지 않는다. 비교 런 ID와 이력 커서에도 DB 범위 제한을 적용한다.

잘못된 ID 및 객체가 아닌 JSON 본문은 422로 거절한다. 잘못된 본문 인코딩은
프레임워크에서 400으로 거절할 수 있다. 인증 모드에서는 유효한 JSON 요청에 대해
로그인·CSRF 확인 후, DB 조회 전에 경로 ID를 검사한다. 로컬 모드에도 ID 제한을 적용한다.
